# Jianwei 开发哲学

本文维护指导产品演进的目标、取舍与经验，供开发 agent 设计和修改能力时使用。具体能力的执行方法由各自的 skill 维护，工作产物的组织规则见 [WORKSPACE.md](WORKSPACE.md)，工程与交付约束见 [ARCHITECTURE.md](ARCHITECTURE.md)。本文不规定固定调用顺序，也不声明尚未实现的能力已经可用。

## 服务于投资理解与高质量选择

Jianwei 为个人提供可组合的投资分析与顾问能力，帮助用户理解问题、比较选择、形成有依据的行动，并持续改善判断。产品聚焦分析与建议的质量；严密的账户核算、个人财务管理、高时间精度的量化交易与自动执行不属于产品范围。新增能力应围绕投资理解与选择产生价值，避免让账务完整性或执行系统的复杂度主导设计。

## 以专业责任划分能力，以组合承接工作流

一项能力应有可独立委托的问题、明确的专业责任和有价值的完成成果。元能力可以包含深度思考和多个步骤，无需拆成细碎动作；新增 skill 的理由应来自独立的用户需要，而非流程中又出现了一个步骤。

独立性允许协作。能力可以使用已有成果，按需请求其他能力参与，并在自己的职责完成后结束。研究应独立评价证据，接受问题但不接受预设答案；表达成果时应保留原有判断的强度与条件。上下游需求不能改变各自的专业标准。

具体任务的参与能力、顺序与衔接方式通过组合形成。反复出现且值得复用的组合，可以固化为工作流；用户个人的习惯性路径应留在组合或用户背景中，保持通用能力可用于其他路径。

## 当前问题决定范围，环境提供背景

从用户本次要解决的问题出发，渐进获取相关信息。工作区中存在某份材料，不意味着它自动成为必做分析：持仓可以是背景，也可以是分析对象；读取持仓不自动扩大为全面组合审查，存在历史也不自动要求复盘。仅在进一步工作会实质影响当前成果时展开。

Agent 主动查找事实、解释问题、比较方案并表达有依据的倾向。目标、约束或重要取舍存在实质歧义时，与用户对齐；已有明确表达应当复用。让人的参与集中于需要人的价值判断与选择之处，同时保留 agent 的思考与自驱性。

## 用专业承诺定义建议质量

顾问应承担比较方案与形成建议的责任，使用户理解推荐什么、依据是什么、需要接受什么代价，以及什么会改变判断。仅罗列风险与选项，或把问题交还给用户，不足以完成这项职责。建议的细度应与任务及依据相称，用户保留重要取舍与最终决定。

既往系统的教训是：当行动承担大量证明要求，而不行动无需说明理由时，系统容易持续退回观望。行动与维持现状都应接受分析，不确定性本身不能决定建议方向。区分有依据的维持、等待、不参与，与尚未形成判断；判断缺口应如实呈现并尽可能解决。

按未知信息对选择的影响决定是否继续调查或提问。补充工作应能改善具体判断，无需等信息完整、预测确定或风险消失才形成建议。交易频率、保守程度与表达的确定性都不能代替质量。

帮助新手改善思考，应落实为比较未来选择、理解价格与机会、考虑整体影响、检验假设等具体行为。避免用“摆脱散户思维”之类的标签预设投资风格。解释应帮助用户逐渐理解和质疑建议，减少对指令的盲目依赖。

## 让环境成为可持续使用的资产

工作区应让新 session 快速找到相关背景，并沿时间和引用逐步理解历史。按实际工作沉淀成果，使一次认真思考能够成为后续工作的起点；不要求用户持续使用或维护完整账本。

历史成果的价值包括当时的依据、条件与不确定性。复用应保留这些语境，能够分辨分析判断、顾问建议与用户实际表达。记录缺失、背景陈旧和现实未变化具有不同含义，设计时应保持这种区别。具体时间、快照、文件与引用规则统一维护在 [WORKSPACE.md](WORKSPACE.md)。

复盘帮助用户理解已经发生的市场与投资经历，解释结果怎样形成，审视认识与选择，为后续投资提供更好的依据。它可以从市场演变或外部材料开始，无需先有个人投资记录。完成价值在于本次分析是否增进理解，无需每次找到错误、提出交易动作或提炼通用经验。

长期保存为后续任务提供查阅与重新思考的机会，不承诺工作区会自动积累判断能力。历史结论与改进建议保留其依据、时间和适用条件，由新问题决定如何使用；避免把过往成功或失败不断变成默认加载的行动前提。能力的方法论由开发者审视与维护，用户工作区中的个案成果不自动成为 skill 规则。

## DRY 与渐进披露

同一知识或约定保留明确的维护位置，其他文档通过有触发条件的阅读入口引用。开发哲学解释设计理由，skill 承担具体专业行为，共享约定维护共同规则；避免复制整段原则来增加其权重。

保留不同时间的快照和判断，以及读懂成果所需的摘要，有各自的语义价值。DRY 不要求把历史压成不断被覆盖的最新版本，也不要求读者重放大量变化才能理解一份成果。

新增文件、字段、能力或协议，应产生明确的使用价值。共同需要的内容保持易于找到，只在特定情境需要的细节按需披露；自然语言与简单文件足够时，优先保持简单。

## 从案例修正设计，避免 skill 过拟合

案例是发现问题和验证改进的材料。将每次失败的分析过程与最直接的补救办法追加到 skill，会逐渐形成重复要求、相互牵制的例外和隐含的特定路径，使能力难以继续演进。文档增长本身不代表能力改善。

遇到失败时，先定位原因：职责或完成标准是否模糊、已有要求是否矛盾或难以发现、必要背景是否缺失、工具或执行是否失败。随后修改真正承担该问题的层次。已有规则足以表达意图时，优先澄清、合并、重写或删除；环境和工具问题在相应位置修复。新增规则应能解释一类问题，并明确何时适用，而不是把单个案例推广为所有任务的前提。

Skill 正文保留稳定的职责、判断方法与完成标准。个案经过、试错记录和详细诊断留在开发记录或评估材料中；确有必要的领域细节按需引用。示例用于澄清难以表达的区别，不承担不断扩大的例外清单，也不预设唯一正确答案。将补丁搬进附录并不能消除过拟合，仍需判断它是否值得成为规则。

评估修改时，既看它能否解决原问题，也看它能否适用于条件不同的任务，并保留其他合理路径。尤其检查是否无意增加必填背景、固定流程、默认观望或特定投资风格。规则之间发生冲突时，重审整体表达，避免继续追加优先级和例外。验证范围与变化相称，评估的执行方式遵循 [QA 约定](../qa/README.md)。

维护的目标是用少量自洽的规则支持丰富情境。把具体案例中的经验提炼成可迁移的判断方法，同时保留 agent 根据任务思考的空间。
